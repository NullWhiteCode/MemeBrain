PURPOSE AND IMPLEMENTATION
ocr.py:extractText checks the lowercased input suffix. For GIFs, it calls the
shared extractGifFrame helper and converts the RGB Pillow image to a NumPy
array for the OCR engine. Other inputs pass their path to the engine.
The helper chooses n_frames // 2, so OCR examines one midpoint frame, not every
frame or the temporal midpoint. createEngine constructs RapidOCR().
extractText joins result.txts with spaces, or returns an empty string when
result.txts is None. Recognition boxes and confidence values are not persisted
by this path.

prepare_ocr_data looks up the indexed file ID and records text, time.time(),
engine name RapidOCR and the installed distribution version. database.py creates
an ocr table with a unique file_id and foreign-key relationship to files.
insertOCRData parameterises its values and updates text, timestamp and engine
metadata on file_id conflict. setupConnection enables foreign-key enforcement.
getPendingOCR selects indexed files with no OCR row. An empty-text OCR row counts
as processed, because pending selection checks row existence rather than text.

processPendingOCR takes a pending snapshot, constructs one engine and processes
the snapshot sequentially. startOCRWorker uses a daemon thread and an is_alive
check. app.py starts OCR from the home route when a library is configured and
from the folder-selection flow. Worker completion is not checked here at runtime.

LIMITATIONS AND UNVERIFIED CASES
The automated checks cover adapter and persistence plumbing in isolation.
Real-engine integration is user-reported above; recognition accuracy remains
limited, including the observed false positive on a no-text GIF.
Changing text across frames, animated disposal/transparency, malformed files,
multilingual recognition and confidence-based filtering remain unverified.
prepare_ocr_data assumes fileLookup returns a row. processPendingOCR has no
per-file exception handler; an exception can terminate that run. Thread races,
database contention, shutdown and restart behaviour were not tested. No retry
or explicit failed-item status is demonstrated by this implementation.
