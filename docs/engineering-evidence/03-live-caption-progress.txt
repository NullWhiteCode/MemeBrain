PURPOSE AND IMPLEMENTATION
database.py:getCaptionProgress uses a LEFT JOIN from files to captions and
returns COUNT(*) and COUNT(captions.file_id), filtered to files.status='indexed'.
The unique captions.file_id prevents multiple caption rows inflating the count.
The aggregate measures caption-row existence, not caption quality or generation
tokens. It covers all indexed database files without a current-folder predicate.

app.py:caption_progress exposes GET /caption_progress. It returns JSON fields
total, completed, pending, percentage and running. Pending is total minus
completed; percentage is completed / total * 100, or zero for an empty total.
running comes from caption.py:isCaptionWorkerRunning and the local thread state.
The aggregate and thread state are read separately, not as one atomic snapshot.

templates/index.html contains .captions-panel with #caption, #progress (max=100),
#info and a POST /generate_captions form containing .generate-caption-button.
static/JS/captions.js fetches immediately and registers a 2,000ms interval. It
updates progress.value, completed/total/pending text and a two-decimal percentage.
Button branches are ordered:
  running: 'Generating...', disabled (source uses a typographic ellipsis).
  otherwise pending > 0: 'Generate', enabled.
  otherwise: 'All captions generated', disabled.
The second condition need not repeat !running because the first branch already
handles running. The POST starts the worker if a library is configured, then
redirects home. Current worker default is five pending files per run.

Current static/CSS/style.css includes caption-specific panel, progress and
button rules. The panel background is blue (#5ea9eb), with a border rule;
progress is 100% wide and 2.5rem high, and the button is 25% wide and 2.5rem high.
These dimensions and colour are source-inspected, not a visual rendering test.

PREVIOUSLY RECORDED SYNTHETIC/AUTOMATED VERIFICATION: PASS
Actual database functions in disposable SQLite returned (0,0) for empty storage
and (2,1) for two indexed files, one caption and one excluded missing file.
The actual caption_progress function was extracted using AST and registered in
an isolated Flask app. Its test client returned HTTP 200 and expected five-field
JSON for partial/running and empty/idle cases. The empty case returned 0 percent.
Thread state was stubbed; the production app module was not imported.
Actual captions.js ran in a Node VM with DOM, fetch and timer doubles. Checks
passed for 2000ms interval registration, percentage formatting, progress value,
running, pending, complete and empty-library button branches. A simulated HTTP
500 was caught and retained the prior display. No real browser timer was run.

USER-REPORTED MANUAL INTEGRATION VERIFICATION
The user confirmed initial Flask JSON counts of 473 total and 24 completed.
Browser DevTools showed repeated HTTP 200 progress requests approximately every
two seconds. During batch processing, completed rose from 24 to 29 and later
to 39; the user observed the button return to idle. These are user-reported
live integration observations, not independently witnessed tests by Work.
Zero-total and all-complete states have not been verified end to end; coverage
of those states is limited to the synthetic/automated checks above.

LIMITATIONS AND UNVERIFIED CASES
Work did not independently run the live browser-to-Flask-to-worker workflow.
An empty library displays 'All captions generated' at 0 percent under current
logic. A stopped five-item batch with pending files returns to enabled Generate.
No ETA, explicit error display or automatic queue-draining is implemented here.
Polling can overlap if requests exceed two seconds; out-of-order responses,
network recovery, multi-process deployment and click races were not exercised.
DOM queries precede the try block and assume the panel exists. Rendering,
accessibility, responsive layout and browser-specific progress styling remain
unverified beyond the user-reported observations above.
